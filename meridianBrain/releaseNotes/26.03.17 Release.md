# 26.03.17 Release

> **Meridian:** WIP / archive — human release notes; not read by CLI or Copilot `#file:`.

Date: 2026-03-17

## Overview

This update brings a strong set of workflow improvements across Salesforce org management, wiki generation, prompt-driven workflows, and ADO template rendering. The overall theme is simple: make the tools easier to use, reduce manual setup friction, and produce more consistent output everywhere the workflow touches.

## Feature: Role-Based Salesforce Org Resolution

### What

This release adds role-based Salesforce org targeting across `sf-tools`. Instead of relying on each person to remember and pass the right alias every time, commands can now target logical roles like `primary`, `legacy`, `modern`, `legacyData`, `modernMetadata`, and `dataCloud`.

The update also introduces:

- Per-developer org role mapping through `config/sf-orgs.json`
- A checked-in starter example at `config/sf-orgs.example.json`
- New org management commands: `org-setup`, `org-status`, and `org-validate`
- Resolver fallback logic so commands can still work even when only part of the role map is configured

### Why

This is a big quality-of-life improvement for anyone working across multiple Salesforce environments. The new model lets the workflow think in terms of purpose instead of alias names, which makes prompts more portable, commands less error-prone, and multi-org work much easier to explain and automate.

## Feature: Interactive Org Setup Experience

### What

The new `sf-tools org-setup` flow walks users through configuration interactively. It detects authenticated orgs from the SF CLI, asks whether the user works in a single-org or multi-org setup, and then assigns aliases to the appropriate logical roles.

For multi-org users, the prompt explicitly asks for:

- Legacy org
- Modern org
- Legacy data org
- Legacy metadata org
- Modern data org
- Modern metadata org
- Data Cloud org
- Primary default org

It then writes the configuration to `config/sf-orgs.json` and immediately validates the saved org aliases.

### Why

This makes setup much more approachable and much less brittle. Instead of editing config by hand or remembering a hidden convention, users can answer a few concrete questions and get a working, validated setup in one pass.

## Feature: New Wiki Engine and Wiki Workflows

### What

This release introduces a new block-based wiki engine and a dedicated `wiki-engine-tools` CLI. The engine supports structured wiki composition with reusable block types such as narrative sections, tables, callouts, bullet lists, numbered lists, link lists, code blocks, Mermaid diagrams, and placeholders.

The new CLI adds:

- `block-menu` to expose supported block types
- `render` to turn a wiki spec into output
- `validate` to check wiki specs before rendering
- `colors` to inspect semantic wiki color schemes

On top of that, the workflow now includes new prompts for wiki operations:

- `/util-wiki-create`
- `/util-wiki-update`

### Why

This is exciting because wiki generation is now a real first-class workflow capability instead of an ad hoc formatting exercise. It gives the team a more repeatable way to create rich, structured documentation and makes it much easier for prompts and tools to produce wiki content that looks intentional and consistent.

## Feature: Shared Nunjucks Template Rendering

### What

The ADO HTML template system has been refactored to render through a shared Nunjucks environment instead of manual token replacement. A new shared rendering layer now handles environment setup, slot-to-context transformation, HTML entity decoding, and non-ASCII encoding for ADO-safe output.

This also brought in reusable partials for common visual patterns such as:

- Gradient headers
- Content cards
- Tables
- Badges
- Progress bars
- Wiki block helpers

Templates like the release notes field now use macros and conditional sections rather than duplicating large inline HTML structures.

### Why

This is one of the most important maintainability wins in the diff. Shared rendering means fewer one-off patterns, more consistency across work items, and safer handling of special characters and encoded content. It should be faster to evolve templates going forward and much easier to trust the final output.

## Feature: Expanded Template Coverage

### What

Template support has been expanded significantly, including additional template-registry coverage for Epic-level reporting fields such as:

- `Custom.Blockers`
- `Custom.Progress`
- `Custom.PlannedWork`

The registry and template assets were also updated to support the broader Nunjucks/partials model.

### Why

This matters because more work item scenarios can now use the same structured formatting system instead of falling back to inconsistent manual content. It pushes the workflow closer to full coverage across the most important ADO authoring scenarios.

## Feature: Prompt and Guidance Refresh

### What

The workflow prompts and guidance were updated to match the new capabilities. That includes changes to help/setup prompts, grooming and solutioning prompts, Copilot instructions, and the addition of new wiki-focused prompts.

The docs were also updated so users can discover and use the new org-role and wiki-engine workflows more easily.

### Why

This is important because new tooling only helps if people can actually find it and understand how to use it. Updating the prompts and docs closes that gap and makes the new features feel integrated instead of bolted on.

## Feature: Standards and Structural Cleanup

### What

This release also updates the standards library by adding `unified-crm-data-standards.md` and consolidating flow naming guidance into `metadata-naming-conventions.md`, removing the separate `flow-naming-conventions.md` file.

### Why

This keeps the standards footprint cleaner and better aligned with the broader architecture and metadata guidance. It is a smaller change than the tooling work, but it supports the same goal of making the repo easier to navigate and maintain.
