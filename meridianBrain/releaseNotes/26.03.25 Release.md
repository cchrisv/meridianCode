# 26.03.25 Release

## Overview

This release adds two new workflow prompts, renames the grooming tag to `Copilot-Refined`, and delivers a focused round of reliability fixes across the ticket grooming phases, apply-template, and utility prompts. The fixes address specific feedback tickets and close several gaps where silent failures, missing prerequisite context, or undefined variables were causing Copilot to loop, skip steps, or produce incomplete results.

## Feature: Meeting Notes Prompt and Template

### What

This release introduces a new end-to-end workflow for formatting meeting transcripts into structured ADO Tasks.

The new `/util-meeting-notes` prompt follows a five-step flow:

- Gather meeting metadata and the raw transcript
- Parse the transcript into structured sections
- Preview the result for user approval
- Render the Nunjucks template into ADO-safe HTML
- Push the fielded content to a new ADO Task

A new `field-meeting-notes.html` template was added with gradient-header sections for meeting metadata, participants, key decisions, next steps, discussion highlights, and the full meeting transcript. The template is registered in `template-registry.json` with eleven named variables.

The copilot-instructions.md was also updated to expose the new prompt in the utilities list and under a dedicated "Format meeting notes" entry point.

A follow-up fix was applied so the prompt always creates a new Task rather than attempting to update an existing one, and explicitly requires a parent work item ID before proceeding.

### Why

Meeting notes were previously handled ad hoc, with no consistent structure and no connection to ADO. This prompt makes the workflow repeatable, links the output directly to an ADO parent, and produces a formatted Task that is immediately useful for tracking decisions and next steps.

## Feature: User Identity Persistence in Setup

### What

`/util-setup` now includes a new **Step 3.5 — Capture & Persist User Identity** that collects the user's ADO display name and email and writes them to `config/shared.json` under a top-level `user` key:

```json
{
  "user": {
    "display_name": "Chris Van Der Merwe",
    "email": "Christiaan.vandermerwe@umgc.edu"
  }
}
```

The step reads back the saved values and confirms with a `✅ Identity saved` message.

`config/shared.json` itself was updated to include the `user` block, pre-populated with the initial identity.

### Why

Previously every prompt that created or assigned ADO work items either asked for the user's name each time or left the `assigned-to` field blank. Persisting identity once during setup removes the repetitive question and ensures consistent attribution across all prompts that create work items.

## Enhancement: Auto-Identity Propagation to Prompts

### What

Three prompts now read `user.display_name` and (where relevant) `user.email` from `config/shared.json` instead of asking each time:

**`/util-morning-checkin`** — Step A2 was updated so `{{person}}` auto-resolves from `user.display_name` / `user.email` when both config values are non-empty. The interactive question is only triggered when the config values are missing.

**`/util-meeting-notes`** — A new step B2.6 reads `user.display_name` from config and uses it as the default `assigned_to`, pre-filling the confirmation question rather than presenting a blank field. The `--assigned-to` argument is now passed at task creation.

**`/util-feedback-review`** Path B — The `ado-tools create` command now includes `--assigned-to` set from `user.display_name`, so new User Stories created during triage are automatically attributed to the running user.

### Why

After identity was made persistent in Step 3.5, the remaining prompts needed to consume it. Without this propagation, the setup step would have had no effect on prompt behavior.

## Enhancement: Meeting Notes – Area Path Inheritance, Computed Metadata, and Task Closure

### What

Three related improvements were made to `/util-meeting-notes`:

**Area Path inheritance** — A new step B2.5 queries the parent work item via CLI and extracts `System.AreaPath`. The inherited value is used when creating the Task rather than the previously hardcoded default. The fallback to `Digital Platforms\CRM - DREAM\Refinement` is used only if the parent lookup fails.

**Computed task metadata** — A new step C1.5 derives four values from the parsed meeting data:

- `completed_work_hours` — meeting duration parsed into decimal hours (e.g., "41m 47s" → 0.70)
- `target_start` — ISO 8601 timestamp combining meeting date and start time
- `target_end` — target_start plus completed_work_hours
- `activity_suggestion` — inferred from meeting context (e.g., `Design`, `Meeting`)

A new step E4b then pushes these computed values — plus `System.State: Closed` — to ADO in a single fields-file update. Meeting Notes Tasks are created and immediately closed as historical records.

**Preview enrichment** — The Step 3 preview now includes Assigned To, Activity, Completed Work, Target Start, Target End, Area Path, and State alongside the existing content summary.

### Why

Meeting Note Tasks were previously left open (no state, no timing data, no owner), which cluttered the active work queue and made sprint reporting inaccurate. Area path inheritance prevents Tasks from defaulting to the wrong team area when triggered from a parent in a different context.

## Enhancement: Feedback – Infrastructure Gap Issue Type

### What

`/util-feedback` was updated to surface a new issue type and auto-detect when it applies.

**New issue type** — `setup/infrastructure gap` is now listed alongside the existing issue types in the Stage 1 question. It is described inline as the appropriate type when the user was compensating for a missing repository, undeployed domain workspace, absent config/environment, or other infrastructure prerequisite that doesn't yet exist.

**Compensating-behavior detection** — A new step A3a scans the current conversation thread for these signals before the interview begins:

- User states something doesn't exist yet (e.g., "we don't have a dedicated repo", "there's no X yet")
- User manually redirecting Copilot across multiple folders or orgs to substitute for missing domain context
- User providing domain knowledge verbally that would normally come from a repository or config file

When any signal is detected, `issue_type` is pre-populated with `setup/infrastructure gap` in the draft packet and flagged in the Stage 3 summary for user confirmation.

**New Stage 2 field** — A "Setup or infrastructure gap" optional field was added to the Stage 2 interview, prompting the user to describe what is missing and when it is expected to be available.

### Why

Infrastructure gaps were often being filed as generic "missing context" or "workflow problem" issues when the real root cause was a missing repository or unconfigured environment. The new type and auto-detection make the classification accurate from the start and give the triage review a clear basis for routing these issues to infrastructure work rather than prompt fixes.

## Fix: Feedback Review – Structured HTML Closing Comments

### What

All three triage paths in `/util-feedback-review` now generate structured inline-HTML closing comments instead of plain text strings. Each path produces a comment using the system's standard gradient header style (dark background, white bold text) and left-bordered content cards consistent with other HTML outputs in the workflow.

**Path A (direct implementation):** Sections — Summary, Root Cause, Files Changed (table), Verification Notes, Next Steps.

**Path B (create User Story):** Sections — Summary, Root Cause, Action Taken (with ADO link to the new User Story), Next Steps.

**Path C (close as not needed):** Sections — Summary, Reason for Closure, Analysis, Next Steps.

In all cases the temp comment file was renamed from `.txt` to `.html`.

### Why

Plain-text comments were inconsistent with every other HTML output in the workflow and rendered without formatting in ADO. The structured format makes closing comments readable alongside other rich content in the work item history.

## Fix: Feedback Review – Successor Link Argument Order

### What

In `/util-feedback-review` Path B, the `ado-tools link` command argument order was corrected. Previously the new User Story was passed as the first argument (source) and the feedback Issue as the second (target), which created the link with inverted predecessor/successor semantics.

The corrected call is:

```
{{cli.ado_link}} <issue_id> <us_id> --type successor
```

The first argument is now the predecessor (feedback Issue) and the second is the successor (User Story), matching the documented CLI convention (`link <predecessor> <successor> --type successor`). An explanatory note was also added inline to prevent future regression.

### Why

The inverted link meant ADO was recording the User Story as the predecessor of the feedback Issue — the opposite of the intended relationship. Work item dependency views and downstream queries that rely on successor links would have returned incorrect results.

## Feature: Feedback Review and Triage Prompt

### What

This release adds `/util-feedback-review`, a new prompt for structured feedback triage and improvement planning. The prompt presents all open feedback Issues, groups them by theme, and guides the user through three paths:

- **Path A** — Close the issue as resolved or declined with a comment
- **Path B** — Create a new User Story to implement the improvement, linked as a successor of the feedback Issue
- **Path C** — Defer for later with a follow-up comment

Path B was subsequently fixed so the created User Story is correctly linked as a successor to the originating feedback Issue and parented under `246209`.

The prompt was also registered in `/util-help` and copilot-instructions.md so it is discoverable by name alongside the other utilities.

### Why

Feedback Issues were accumulating in ADO without a consistent review cadence or a clear path from triage to implementation. This prompt gives the team a repeatable way to work through the backlog of feedback, close what is resolved, and surface actionable improvements into the grooming pipeline.

## Fix: Diagnostic Prerequisite Gates Across Grooming Phases

### What

All four ticket-grooming phases previously had a bare one-liner STOP instruction when a prerequisite was missing:

> STOP if any prerequisite missing. Log to run_state.errors[] and save.

This gave Copilot no information about which key was missing, which phase produces it, or how to recover — causing infinite loops when users re-invoked the same blocked phase.

Each phase now classifies prerequisites as either a **hard blocker** or a **soft miss**:

- **Hard blockers** — present an interactive question with two explicit recovery options: re-run the missing phase, or continue with reduced context
- **Soft misses** — log a warning to run_state.errors[] and continue without halting

Each missing key is mapped to the phase that populates it and the exact CLI command needed to recover.

Phase-by-phase breakdown:

| Phase                     | Hard blockers                                                  | Soft misses                                                               |
| ------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 02 — Grooming             | `research.synthesis`, `phases_completed[research]`             | `research.assumptions`                                                    |
| 03 — Solutioning Research | `phases_completed[grooming]`, `grooming`, `research.synthesis` | `wiki_search`, `team_impact`, `ado_workitem`, `solutioning_investigation` |
| 04 — Solutioning          | `phases_completed[research/grooming]`, `grooming`, `synthesis` | `salesforce_metadata`, `dependency_discovery`                             |
| 05 — Finalization         | `phases_completed[solutioning]`, `grooming`, `solutioning`     | `research`                                                                |

Resolves: #266952

### Why

The old pattern was not actionable. When Copilot stopped on a missing prerequisite, the user had no way to know what was missing or what to do next. The new gates surface a clear diagnosis and give the user a concrete choice rather than a dead end.

## Fix: Phase 05 Finalization Reliability

### What

Three separate reliability gaps in the Phase 05 finalization flow were closed in this release.

**Rev check (resolves #266766):** Step F1 was split so System.Rev is captured before the ADO update. After the update, a new step compares the revision and stops with a clear error if the revision did not increase — the same silent-failure detection pattern applied to `/util-apply-template`.

**Field verification:** A new step explicitly compares the StoryPoints, Priority, and Tags values fetched from ADO after the update against the WSJF-calculated values. Any mismatch is flagged to run_state.errors[] before the completion summary.

**Formatting guidance:** The completion summary now always includes a note that Description and Acceptance Criteria formatting is Phase 02's responsibility, and directs the user to re-run Phase 02 or `/util-apply-template` if formatting is missing.

**Tags construction (resolves #266808):** A new logic step explicitly constructs `final_tags` by fetching `System.Tags`, splitting on `;`, trimming whitespace, appending `{{tags.refined}}` if not already present (case-insensitive), and joining back with `; `. The constructed value is logged for traceability. Previously, the `Copilot-Refined` tag was being silently dropped because no step fetched `System.Tags` or built the `final_tags` variable.

### Why

Phase 05 is the last step in the grooming pipeline and the one most likely to be trusted without verification. These fixes make the phase self-checking so silent failures in ADO updates, missing tags, or miscalculated WSJF fields surface immediately rather than being discovered later during review.

## Fix: Apply Template Silent Failure Detection

### What

`/util-apply-template` was updated to close a verification gap that allowed false-positive confirmations when ADO silently made no change.

Updates include:

- Step A6: added a note that ADO `WorkItemType` of `Defect` maps to the Bug/Defect template row
- Step C8 (new): extracts `System.Rev` from the `ado-tools update` response and stops if the revision did not increase
- Step D2: replaced subjective visual HTML inspection with a three-part explicit verification — rev comparison against backup, linear-gradient signature check per field, and before/after character count report with a halt on failure

Resolves: #266721

### Why

The previous D2 step relied on visual inspection with no baseline, which meant a failed or no-op ADO update could pass the check. Adding a definitive rev comparison and character count removes ambiguity and makes failures recoverable before the session closes.

## Feature: Unified Copilot Grooming Workflow

### What

This release introduces `workflow-initial-copilot-grooming`, a single unified prompt that replaces the two separate pipelines — the 5-phase ticket grooming pipeline and the 7-phase feature research pipeline.

The new workflow is organized around five fluid concerns:

1. **Discover** — ADO research, SF discovery, wiki search
2. **Refine** — requirements authoring (What/Why, not How)
3. **Solve** — solution design and options analysis
4. **Size** — WSJF scoring and story point estimation
5. **Publish** — ADO field updates, wiki documentation

The workflow accepts three input modes and scales depth automatically:

| Input                              | Discovery Depth                                         | Output                                     |
| ---------------------------------- | ------------------------------------------------------- | ------------------------------------------ |
| User Story / Bug / Defect          | Conditional SF                                          | Groomed ADO work item                      |
| Feature / Epic (with SF objects)   | Deep SF (schema + automation + architecture + platform) | Groomed ADO work item + wiki documentation |
| SF objects only (no ADO work item) | Full SF research                                        | Wiki documentation only                    |

Historical note: a companion planning document (`plan-ticketGroom.prompt.md`) once captured migration rationale; it has been removed in favor of the unified `workflow-initial-copilot-grooming` prompt.

### Why

The old separation created two overlapping pipelines with duplicated research patterns. Both pipelines did ADO research, SF discovery, and synthesis — the only real difference was depth and output artifacts. Merging them into one concern-based workflow eliminates the duplication, removes the friction of choosing the right pipeline, and makes the grooming experience consistent regardless of work item type.

## Feature: Dev True-Up Utility

### What

`/util-dev-trueup` is a new standalone utility that reconciles planned vs actual after development is complete. It works on any ADO work item — whether or not it went through the full grooming pipeline.

The utility:

- Fetches the work item, existing context file (if present), and all linked PRs
- Analyzes PR diffs and Copado deployment evidence
- Conducts a structured developer interview at each gate
- Updates Description, Acceptance Criteria, Solution Design, and Release Notes fields with as-built reality
- Appends the `Dev-Complete` tag and pushes a single combined ADO update

It replaces `ticket-grooming-phase-06-dev-closeout.prompt.md`, which has been removed.

### Why

Dev closeout was previously tightly coupled to the grooming phase sequence. As a standalone utility, it can be used independently — before, after, or completely outside the grooming pipeline — which is more realistic for how development actually closes out.

## Feature: ADO Iteration CLI Command

### What

A new `ado-tools iteration` command was added to the CLI. It retrieves iteration dates and validity for a given iteration path, with optional depth control for child iterations.

A `--list` flag enumerates all iterations under a given root path, and a `--validate` flag checks whether an iteration is currently active (within its start/end date range).

A new `adoIterations.ts` source module backs the command.

### Why

Iteration context was previously only available by reading raw ADO area configuration. The new command makes it accessible in a structured, JSON-compatible form that prompts and reports can consume directly — useful for validating that a target iteration is open before assigning work items.

## Feature: Comment-File Option for ADO Update

### What

`ado-tools update` now accepts a `--comment-file <file>` option that reads comment content from a file rather than requiring it to be passed inline. When `--comment-file` is provided it takes precedence over `--comment`.

### Why

Long or multi-line comments are impractical to pass as inline strings through the CLI. This option enables prompts and scripts to write comment content to a temp file and pass the file reference instead — the same pattern already used by `--fields-file` and `--from-filled`.

## Feature: Config Directory Restructuring

### What

The flat `config/standards/` and `config/templates/` directories have been reorganized into three platform-scoped directories:

- `config/core/` — Core standards, share blocks, and cross-platform templates
- `config/platform-ado/` — ADO-specific standards, templates, and share blocks
- `config/platform-salesforce/` — Salesforce-specific standards and share blocks

`config/shared.json` has been updated throughout:

- `paths.templates` now points to `config/platform-ado/templates`
- `paths.standards` is now an object with `core`, `ado`, and `salesforce` keys
- All existing prompts and CLI references updated to use the new paths via `{{paths.standards.*}}`

### Why

The flat structure mixed platform-specific and cross-platform assets in the same directory, making it harder to scope what a given prompt or standard applied to. The new structure makes dependencies explicit, improves discoverability, and aligns with the platform-scoped share block model already in use.
